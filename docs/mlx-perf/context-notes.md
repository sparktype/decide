# 로컬 MLX 성능 개선 컨텍스트 노트

## 2026-10-06
- 사실: Cloudflare가 낸 clef-flash 중앙값 38.8ms는 서버 GPU 기준이다. 이 저장소의 M1 Max 실측(150토큰 0.6초, 900토큰 2.8초)과 조건이 달라 직접 비교하지 않는다.
- 사실: 2026-10-04 노트에 "백본 약 90%, 헤드 40~130ms, 헤드를 GPU로 옮겨도 이득 작다"는 계측이 이미 있다. 그래서 헤드 이전은 이번 범위에서 뺐고, accelerate로 CPU GEMM만 싸게 시험한다.
- 결정: 계측은 thread_local lap 기록 + `DECIDE_LOCAL_TIMING` 환경변수로 켠다. 이유는 `score`/`head_inputs`/`hidden_states`의 시그니처를 건드리지 않기 위해서다.
- 결정: 선로딩은 `serve_unified`가 아니라 `serve_default`에서 건다. `serve_unified`는 테스트가 키 없는 환경에서 호출하는데, 그 환경은 local 백엔드로 해석돼 테스트가 10GB 모델을 올리게 되기 때문이다.
- 작업 위치: 체크아웃이 다른 세션과 공유되므로 worktree `../decide-perf`(브랜치 `perf/mlx-warmup`)에서 진행한다.

## 2026-10-06 (실측, M1 Max, release)
- 사실: 웜 상태 백본 eval이 전체의 92~94%다(145토큰 464ms, 861토큰 2277ms). 호스트 복사는 0.2~1.4ms라 문제가 아니다. 앞서 "복사 비용이 클 것"이라고 한 추정은 틀렸다.
- 사실: 헤드는 accelerate 전 36ms/117ms, 후 33ms/58ms. 긴 입력에서만 절반으로 줄고 전체 지연으로는 약 2.5%다. 비용이 작아서 유지한다.
- 사실: 선로딩 전 첫 호출 3.76초(load 638ms + backbone 2.8초 + head_tensors 265ms). 선로딩 후 첫 요청은 499ms로 웜(497ms)과 같다. 단, 이 콜드 수치는 OS 파일 캐시 상태에 크게 좌우된다(두 번째 측정에서는 콜드가 1.07초로 줄었다). accelerate 효과로 해석하지 않는다.
- 사실: 선로딩은 프로세스 안에서만 검증했다. 사용자의 기존 `decide daemon`(brew, PID 25520)이 기본 소켓을 쥐고 있어 새 빌드의 데몬 종료·교체를 하지 않았다. 새 빌드를 설치하면 데몬 교체 뒤 첫 요청 지연을 직접 확인해야 한다.
- 사실: 기본 스위트 237 통과, parity 5/5 일치(최대 로짓 차이 0.0948, 기존 0.095와 동일).
- 결론: 웜 지연의 대부분은 백본 prefill이다. 다음 큰 이득은 `decide_many`의 state 접두 재사용(질문 N개일 때 prefill N배 → 1배)이고, 헤드 이전이나 4bit는 웜 지연에 거의 영향이 없다.

## 2026-10-06 (접두 재사용 설계)
- 결정: 접두는 첫 세 Text 세그먼트(시스템 프롬프트, state, `SCHEMA FIELDS`)다. 네 번째 세그먼트부터 질문 종류(`TYPE:`)에 따라 달라진다.
- 결정: 접두 캐시는 `infer_many` 호출 안에서만 산다. 호출 사이에 state가 같은 경우를 위한 데몬 단위 캐시는 이번 범위 밖(필요하면 측정 후).
- 결정: 헤드 입력은 접두 은닉 상태를 host에 보관했다가 접미 뒤에 이어 붙인다. 헤드의 `memory_projection`을 접두 구간만 캐시하는 최적화는 헤드가 웜 지연의 5% 이하라 하지 않는다.
- 가정(테스트로 검증): MLX `scaled_dot_product_attention`의 `Causal` 마스크는 쿼리 길이가 키 길이보다 짧을 때 오른쪽 아래 정렬이다(키 길이 - 쿼리 길이만큼 offset).

## 2026-10-06 (접두 재사용 구현·실측)
- 사실: 가정이 맞았다. MLX `Causal` 마스크는 쿼리가 키보다 짧을 때 오른쪽 아래로 정렬된다(단위 테스트로 확인). conv·delta 상태 이어받기도 분할 계산이 전체 계산과 일치한다.
- 사실(중요): MLX 스트림은 만든 스레드에서만 쓸 수 있다("There is no Stream(cpu, 0) in current thread"). 실제 가중치 테스트를 병렬로 돌리자 다른 스레드에서 모델을 쓰면 실패했다. 이전에 넣은 데몬 선로딩(별도 스레드에서 로딩)과 통합 데몬의 UDS·HTTP 두 스레드가 모두 이 문제에 노출돼 있었다. 선로딩 커밋(`0e73146`)만으로는 데몬에서 요청이 실패했을 수 있다.
- 결정: 모든 로컬 작업(로딩, 선로딩, 추론)을 `decide-local` 전용 스레드 하나에서 돌린다(`on_worker`). 작업 패닉은 `catch_unwind`로 막아 스레드가 살아남는다. 인자는 소유값으로 복사해 보낸다(질문·state 복사는 추론 시간에 비해 무시할 수준).
- 사실: 질문 4개, state 약 865토큰. 질문별 따로 9572ms, 접두 공유 3767ms(2.54배). 접두 765토큰 계산 2037ms, 질문당 접미 약 100토큰 415~452ms. 답 차이는 0.0005 이내이고 `choice`는 같다.
- 사실: 접두+접미 은닉 상태와 전체 계산의 최대 차이는 1.56(최대 절댓값 62.5의 2.5%)이다. 이후 헤드 출력 차이는 0.001 미만이라 판단에는 영향이 없다.
- 사실: 기본 스위트 241 통과, parity 5/5 일치(최대 로짓 차이 0.0948 불변).
- 미검증: 새 빌드를 설치한 데몬에서 UDS와 HTTP를 번갈아 부르는 실제 시나리오. 기존 데몬이 떠 있어 교체하지 않았다.
- 남은 후보: 호출 사이에 같은 state를 재사용하는 데몬 단위 접두 캐시, 접미 약 100토큰(꼬리 고정 문자열 포함)의 추가 절감.

## 2026-10-06 (4bit 체크포인트 실측)
- 대상: `mlx-community/clef-flash-4bit`(bits 4, group 64, affine, 약 6.2GB, 샤드 2개 + `joint_head.safetensors`). `DECIDE_LOCAL_REPO`로 지정하면 코드 변경 없이 로딩된다.
- 사실: 웜 백본 eval은 8bit와 같다(145토큰 461ms 대 464ms, 861토큰 2241ms 대 2277ms). prefill이 compute-bound라 비트 수를 줄여도 빨라지지 않는다. 얻는 것은 디스크·메모리(약 10.7GB 대 약 6GB)다.
- 사실: parity 게이트(질적 판단 일치)는 5/5 통과지만 원시 로짓 최대 차이가 1.157로 8bit의 0.095보다 약 12배 크다. score 케이스 "응답이 평소보다 느립니다"에서 레벨별 로짓 차이가 0.86~1.16이다.
- 사실: 확률이 눈에 띄게 퍼진다. 같은 choice 질문(865토큰 state)에서 infra 확률이 8bit 0.844, 4bit 0.599이고 billing은 0.154 대 0.399다. 1위는 같지만 `confidence` 임계값을 쓰는 호출에는 영향이 있다.
- 사실: 접두 재사용은 4bit에서도 2.58배(9698ms 대 3754ms)이고 접두 사용/미사용 답 차이는 0.01 이내다.
- 결론: 기본은 8bit를 유지한다. 4bit는 메모리가 제약일 때 `DECIDE_LOCAL_REPO`로 선택하는 옵션이며, 4bit 기준으로 `confidence`/`noul` 임계값을 따로 보정해야 한다(두 백엔드가 서로 보정돼 있지 않다는 기존 원칙과 같다).

## 2026-10-06 (오프라인 사무실·응답 성능 우선 후보 조사)
- 조건: 사무실은 외부 인터넷이 없고 맥은 M2 Pro 32GB다. 응답 성능(지연) 우선, Clef 이외 모델을 원했다. M2 Pro는 이 개발 Mac(M1 Max)보다 GPU 연산이 약 0.65배라 같은 모델의 지연은 약 1.5배로 본다.
- 사실: Decision Index 0.2.1에서 Clef 61.21(자체), Jev 57.91(독립), Clef-flash 57.1, Von 13.74. Von은 가장 빠르지만(A10G 23ms) 정확도가 판단 도구 수준이 못 된다.
- 후보: Kev-4B(Qwen3.5-4B + LoRA, Apache-2.0, MLX 네이티브, 255옵션, 8k 컨텍스트, breadth-v1 0.690 대 Jev 0.757). M5에서 5질문 721ms, 같은 텍스트 반복 시 136ms(서버가 state를 캐시). 메모리는 약 9GB(어댑터 병합 시 적재 순간 약 16GB).
- 제외: NeoHorse-Jev-4B(state 384토큰 제한, MLX 없음), Nimble-9B-v3(CC BY-NC), JEV-27B(54GB), Kev-27B(51GB, 32GB Mac에 불가).
- 결정: Kev는 TypeSafe `/v1/systemone`과 같은 형식이라 `decide` 코드는 `DECIDE_TYPESAFE_URL` 한 줄로 연결한다(`live_transport`). 키는 비어 있지 않은 임의 값(예: `local`)을 `TYPESAFE_API_KEY`로 준다.
- 미완: Kev 서버 실행(`uv run --extra serve python -m kev.serve --run jaredpalmer/kev-4b --port 8009`)은 자동 모드 분류기가 외부 코드 실행으로 거부했다. 사용자 승인 뒤에 이어서 측정한다. 의존성(`uv sync --extra serve`)은 scratchpad의 클론에 설치돼 있다.
